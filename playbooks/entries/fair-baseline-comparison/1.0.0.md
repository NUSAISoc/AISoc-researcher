# Fair Baseline Comparison

## Purpose

Ensure that a claimed improvement over a baseline reflects the method under test,
not an accidental advantage in tuning, compute, data, or reporting. A fair
baseline comparison makes the comparison itself defensible before any result is
believed.

## When to use (applicability conditions)

Use whenever a project reports that a new method beats an existing approach on a
shared metric: model changes, algorithmic changes, prompt or pipeline changes, or
configuration changes. It applies both to internal ablations and to comparisons
against published numbers.

## Inputs

- The candidate method and at least one baseline method.
- A fixed evaluation dataset or task, with a documented split.
- A primary metric agreed in advance, plus the compute or query budget available
  to each arm.

## Procedure

1. Fix the evaluation set, split, and primary metric before running either arm.
2. Give the baseline the same tuning budget, compute, and data access the candidate
   receives; tune both with the same protocol.
3. Run each arm with multiple seeds; record every seed and configuration.
4. Report the metric with a measure of variation across seeds, not a single best run.
5. State any place the candidate had an advantage the baseline did not, and correct
   it or disclose it.

## Expected artifacts

- A comparison table listing each arm, its budget, its seeds, and its metric with
  variation.
- The tuning protocol applied identically to every arm.
- A short statement of residual, disclosed asymmetries.

## Failure modes

- Tuning the candidate hard while using the baseline's defaults.
- Reporting the single best seed of the candidate against the mean of the baseline.
- Silently changing the metric, split, or budget between arms.
- Comparing against a published number produced under a different protocol.

## Evidence and validation status

Emerging: widely recommended in the benchmarking literature and used across a few
internal projects, but not yet validated as a standard procedure in this registry.

## Limitations

Does not by itself establish statistical significance; pair it with a
statistical-analysis playbook. It also cannot fix a poorly chosen metric, only a
poorly run comparison.

## Compatibility

Assumes a harness that can run multiple seeds and record per-run configuration.
Declared compatibility is a lower bound, not a guarantee against future changes.
