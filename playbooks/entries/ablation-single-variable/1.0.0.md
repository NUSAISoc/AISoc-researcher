# Single-Variable Ablation

## Purpose

Attribute an observed effect to a specific component by changing exactly one
variable at a time. Single-variable ablation turns "the system improved" into "this
part of the system caused the improvement", which is what a causal claim requires.

## When to use (applicability conditions)

Use when a system has several components or design choices and you need to know
which ones matter. It applies to model components, features, hyperparameters,
pipeline stages, and prompt elements.

## Inputs

- A working full system and a way to disable or replace one component at a time.
- The same evaluation set, split, and primary metric used for the full system.
- A list of the components or choices to be ablated.

## Procedure

1. Establish the full-system result under the fixed evaluation protocol.
2. For each component, produce a variant that differs from the full system in that
   one component only, holding everything else constant.
3. Run each variant with the same seeds and budget as the full system.
4. Compare each variant to the full system on the primary metric, with variation
   across seeds.
5. Attribute the metric change to the ablated component only when no other variable
   moved.

## Expected artifacts

- An ablation table: one row per variant, naming the single changed component and
  its effect on the metric with variation.
- A record confirming that each variant changed exactly one variable.

## Failure modes

- Changing two things at once, so an effect cannot be attributed.
- Re-tuning other components after an ablation, which reintroduces confounds.
- Ablating only components expected to help, ignoring ones expected to be neutral.
- Reading a within-seed-noise difference as a real effect.

## Evidence and validation status

Established: single-variable ablation is a standard, repeatedly validated method for
component attribution across the experimental machine-learning literature.

## Limitations

Ablations show marginal contribution given the rest of the system; they do not
capture interactions between components. Strong interactions require a factorial or
interaction-aware design instead.

## Compatibility

Assumes a harness that can construct variants differing in one component and run
them under an identical protocol. Declared compatibility is a lower bound.
